The research behind
FrameWorkers

FrameWorkers is a multi-agent system: rather than asking one model to do everything, video production is divided among many specialized AI agents — each owning a single job — coordinated toward one shared goal. Three modules make it work. A trained Director plans the production and re-plans it on failure. An Assistant executes each step and grounds the result in a shared workspace. And a catalog of specialist sub-agents — the crew — does the creative work. Together they replace a fixed pipeline with a closed, recoverable loop.

Why not a fixed pipeline

Real video-making is a multi-step workflow — scripting, asset management, cross-shot consistency — and different inputs call for different workflows. A hand-wired pipeline is brittle, and a zero-shot LLM struggles with long-horizon planning and multimodal asset routing. FrameWorkers instead treats video creation as dynamic task management: every task flows through the same closed loop.

1

Plan

The Director edits the task stack from the intent, agent descriptors, and current state.

2

Execute

The Assistant resolves inputs from the workspace and invokes the right specialist agent.

3

Check

Outputs are parsed, validated, and written back as assets, memory, and logs.

4

Re-plan

On failure, the Director revises the remaining tasks — recover, don't restart.

Module 1 · Planning

The Director & the dynamic task stack

The orchestrator. It reads the brief, the agent descriptors, and the current state, then edits a dynamic task stack — adding, reordering, and revising future tasks. It plans per request and re-plans on failure, never a hard-coded graph; completed work stays as an immutable, auditable history.

And it is trained, not just prompted: zero-shot LLMs misjudge task order and skip necessary steps on long workflows, so we fine-tune the Director with supervised and reinforcement learning over simulated and dynamically generated execution data — until it selects the right agents, orders them by dependency, and recovers from failures.

Module 2 · Execution

The Assistant & the workspace

The execution runtime. It resolves each task's inputs, invokes the chosen agent, validates the output, and persists everything to a shared workspace — files, generated assets, global memory, and logs. A “strict-out, loose-in” contract keeps agents decoupled and recoverable.

Execution robustness

Once the Director has a plan, can the Assistant actually carry it out end to end — every agent call completing, every output validating, nothing lost to a workspace error? Case-level pass rate on a 204-case stratified suite, by the LLM backend powering execution.

Module 3 · The crew

A catalog of sub-agents

Capability as a catalog, not a graph. Each sub-agent is a self-contained module owning one capability, described by its inputs, outputs, and trigger conditions. Routing is semantic, so new capabilities are added by registering a descriptor — no workflow redesign. The Director selects and orders a subset for each production — these are the agents in active use today.
